# test-part: part-probe: real-part core for the 'minimal unrelated circuit' portability fixture (TI TMP1075DR, SOIC-8)

## Summary
Recommended fixture core: Texas Instruments TMP1075DR, an I2C/SMBus LM75-compatible temperature sensor in SOIC-8 (TI package D, drawing D0008A 4214825/C, JEDEC MS-012 variation AA), packed as 2500 LARGE T&R. It is Active per the datasheet's Package Option Addendum dated 17-Sep-2026. The manufacturer-primary datasheet (SBOS854F, Rev F, REVISED JUNE 2024, 49 pages) downloads without login or special headers. I fetched it three times; each copy was byte-identical (sha256 266c9a50…0cf2, 2,813,742 bytes, starts with %PDF-). TI regenerates this PDF even when the revision does not change: HTTP Last-Modified is 18 Sep 2026 while the revision is June 2024, because the orderable-part addendum is appended live. So the retained sha256 is a snapshot of one retrieval. Fixture tests must never re-hash the live URL. A drift re-check belongs only in the explicit source-refresh workflow.

The fixture exercises the v1 contract as follows. .claude/skills/component-spec-audit/references/schema.json:5 requires physical_pdf_page_index plus printed_page_label per source. That index is 0-based: validate.py:412 requires >=0, and existing data such as src-al8860-ds39014 pairs index 1 with label '2 of 18'. Each source row carries one locator, so the LED corpus splits one document into several source records for different pages (for example src-stusb-ds12499 and src-stusb-ds12499-ratings). ## risks
- The datasheet's live bytes change. TI regenerates the PDF: Last-Modified is 2026-09-18 and the addendum is dated 17-Sep-2026, while the revision is June 2024. A future fetch of either URL may hash differently without any revision change. Fixture tests must stay offline and validate against the recorded sha256 and extracts. A source-refresh command must treat a hash change at the same revision as 'regenerated, re-verify locators', not as corruption.
- Do not redistribute the PDF. The LED contract (component-spec-audit/references/contract.md:13) says to keep 'a normalized, minimal evidence extract … without redistributing a PDF'. The fixture should commit sha256 + locators + extracts, not tmp1075.pdf. Any 'retention' test that needs the bytes must be opt-in and online.
- There is no WRL in the KiCad 9.x official 3D library. The LED viewer and publication path accept WRL only (model-assets.ts:48,81; model-descriptor.ts:16). There are three options:
  - Vendor the tag-8.0.9 STEP+WRL pair (recommended; consistent 2017 StepUp geometry).
  - Convert the 9.0.9 STEP to WRL with an extra tool. This adds a dependency and creates a 'derived' fidelity asset.
  - Extend the viewer to render STEP. That is a larger change.
  Pairing the 9.0.9 STEP with the 8.0.9 WRL would give mismatched provenance. The two STEP files differ in bytes and generator.
- Pin to KiCad tag 9.0.9, not master. kicad-footprints master is already KiCad-10 format (version 20260206, ${KICAD10_3DMODEL_DIR}), and the pinned kicad/kicad 9.0.9 renderer may reject or misrender it. Any acquisition script that tracks master will break the preview pipeline.
- The footprint choice can be read two ways. The KiCad symbol TMP1075D defaults to SO-8_3.9x4.9mm_P1.27mm (NXP-derived pads 1.75×0.6 @ ±2.575). The JEDEC-matching footprint is SOIC-8_3.9x4.9mm_P1.27mm (1.95×0.6 @ ±2.475). TI's example land pattern is different from both (1.55×0.6 @ ±2.7). The fixture must record an explicit footprint decision and label it 'generic IPC/JEDEC land pattern, not manufacturer land pattern'. Otherwise a validator comparing pad geometry to the TI drawing will flag a mismatch.
- The part has an LCSC number (C2878381). Tests that use it as a 'non-LCSC' proof must deliberately omit the C-number under the generic profile. Reviewers may object that 'the part has a C-number'. State in the fixture README that this is intentional, to exercise DigiKey/Mouser identity. Never fabricate or blank it under the LED v1 profile to evade the check.
- The Mouser order code 595-TMP1075DR is unverified: the page is bot-blocked. The DigiKey codes were verified only through WebFetch, because curl gets 403. A CI test must not fetch distributor pages.
- The model-publication code hard-codes the LED corpus: model-assets.ts:37-41 fails unless there are exactly 25 selected packages. A one-part fixture will fail there until that count comes from the project config. This is a coupling for the extraction planner, outside part selection.
- Previews need a large image. The KiCad Docker image is not local, is about 476 MB compressed, and is linux/amd64 only. Regenerating footprint SVGs for the fixture requires pulling it, or ARM emulation. The fixture should commit the generated SVG plus its manifest so ordinary checks never need Docker.
- License: KiCad library files are CC-BY-SA 4.0 with a design-use exception. The exception does not apply to redistributing the library 'as a collection'. Vendoring one footprint and one model pair into a fixture is ordinary use, but keep the license header and add a provenance note (tag, URL, sha256).
