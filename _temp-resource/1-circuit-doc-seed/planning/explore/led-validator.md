# led-validator: Canonical Python component-evidence validator (component-spec-audit/scripts/validate.py + test_validate.py), circuit-spec-integration rules/forward tests, component bundle template, representative bundles, and the TS subprocess wrapper (doc/component-docs/adapters/circuit/validate.ts), audited at zudo-led-lamp HEAD 194d8a297e3545588197342130c3111a66c10973 (same commit as the seed)

## Summary
validate.py (1135 LOC, stdlib only) is one monolith. Its generic v1 core is source/fact/pass-trust/bundle/coverage/routing/interaction/pin-map/arithmetic, at validate.py:402-746. Around that core sit LED-only gates that validate_all() (validate.py:1098-1114) always runs, with no switch to turn them off. Things I measured in a scratch copy: (1) the real LED corpus passes the validator, all 38 unit tests and check_forward_tests. (2) The validator itself runs unchanged on Python 3.9, 3.10, 3.11, 3.12 and 3.14 and fails on 3.8 with 'unsafe generator syntax: Index'. So '>=3.12' is only a CI-parity pin, enforced by validate.ts:32 and component-spec-skills.yml:62. The language floor is 3.9. (3) An empty project fails the CLI before any contract check: generator_inventory() ignores the inventory's generator_specs (validate.py:239/247) and falls back to the three LED board specs through `specs or (...)` (validate.py:194-198), even when passed `()` or `[]`. Even with that bypassed, empty data still fails several gates: StopIteration in validate_real_pin_locks:819 (not caught by main:1125, so the user sees a traceback), 'critical fact review: empty' (:829), 'refresh evidence: empty' (:873), fixed LED domains (:912-914), an all-OPEN evidence chain rejected because generated-netlist must be MIXED (:896-897), and 4 invalid fixture cases that target LED line IDs (fixtures/invalid/contract-cases.json, run at :1047-1052). (4) The seed's two bugs are confirmed with reproductions. fact_blocks_domain (:563-566) treats NOT APPLICABLE + SOURCE UNAVAILABLE as blocking, which contradicts contract.md:9, the schema.json blocking_fact_ids_contract and the function's own comment at :564. resolve_identities rejects more than one MPN match at :317, before the manufacturer filter at :374-381. Prototype fixes for both change no LED result: all LED gates still pass, and no corpus fact hits the NOT APPLICABLE edge. (5) New defects the seed missed. `--online` (refresh all) can never pass on today's corpus: 6 AVAILABLE VOLATILE-HTML sources hit the HASH-LOCKED require at :1092, and the run fails deterministically at src-c470643-jlcpcb after 12 fetches. expected_mpn's C144397 special case (:227-228) is dead code, because no generator spec contains C144397 since d892e13. looks_like_vendor_hint hard-codes the LED board names (:283). external_vendor_tokens requires a non-empty vendor list (:298), so a project's first component forces a fake vendor entry. validate_bundle's allow_synthetic_line parameter is never used (:602). source.record_id is enforced (:653) but missing from schema.json source_required. Online temp files go to ROOT/tmp/pdfs (:1078), and the unit test at test_validate.py:374 creates that directory. check_forward_tests.py relies on `assert`, so `python -O` disables it, and it crashes with IndexError when there are no cases (:104). (6) Generator reading is a pure AST interpreter (ComponentDsl :74-185). It never executes the spec, and neither the validator nor pin-asset checks need KiCad: KiCad .kicad_sym/.kicad_mod files are parsed as text with regexes (:749-797). Only schgen verify.sh needs kicad-cli, and the validator never calls it. (7) The TS wrapper calls execFile(python, [scriptPath]) with cwd set to the repo root, never passes --online, and consumes only the exit code (validate.ts:40-71; pipeline.ts:144 turns a failure into VALIDATION_FAILED). Some LED docs contradict the code: validate.ts:15 and ARCHITECTURE.md:198 say online mode 'mutates retained evidence', but it does not (store_and_verify :1063-1068). evidence.ts:248 and integration.test.ts:297 say rules.json is 'not covered by validate.py', but validate_integration_artifacts :903-940 validates it. ARCHITECTURE.md:756 shows a stale 'PASS: 34 lines'. Proposed split: a generic v1 contract package, inventory providers (manual / led-generator-v1), generic integration-rule validation, and data-driven project policy. The LED assertions move to fixtures/led/policy.json. circuit.config.ts reaches Python as a JS-resolved absolute-path JSON file passed with --config. JS finds the script with new URL('../python/', import.meta.url), the same pattern zudo-sg uses in create-zudo-sg/src/scaffold.ts:22.

## risks
- The v1 contract prose and the implementation disagree on NOT APPLICABLE blocking (validate.py:563-566 vs contract.md:9). Rule 'keep the v1 evidence contract unchanged' is ambiguous here: fixing the code to match the frozen prose is corpus-neutral (measured), but it still changes validator behavior. It needs an explicit decision plus a regression test in both directions.
- The resolver fix (manufacturer narrowing before the >1 MPN rejection) is corpus-neutral for LED (measured). validate_routing's positive-query generator (:396) must also change for duplicate-MPN lines: skip the bare-MPN positive and assert bare MPN -> []. Otherwise a generic project with two same-MPN parts can never pass routing.
- validate_all is monolithic and unconditional (:1098-1114). If the package keeps it as-is and adds an 'if profile' in a few places, LED-only assertions (STUSB UNSOURCED :819, AL8860 EP :820-822, 8 domains :912, MIXED netlist :896, last-5 OPEN :900, critical domains :831, refresh classes :883) could leak into generic runs, or could be silently skipped in LED regression runs. Each must move into fixtures/led/policy.json with a test proving the LED run still enforces it.
- Uncaught exception types (KeyError/TypeError/StopIteration/IndexError) make malformed project files crash with a traceback instead of 'FAIL:'. Generated projects must 'fail on malformed/missing declared files', so the new CLI needs a normalized top-level handler with a tested exit code, not one that depends on traceback text.
- Running Python from node_modules: without -B/PYTHONDONTWRITEBYTECODE, __pycache__ gets written into the installed package, and pnpm hard-links package files from its store, so the store is affected. The LED wrapper does not set this today, and the LED repo already contains scripts/__pycache__.
- test_validate.py setUp (:19-22) makes every test, including the 23 generic ones, depend on the LED corpus and board specs. A naive copy into the package makes generic tests unrunnable without fixtures/led. The online-refresh test (:374) creates ROOT/tmp/pdfs as a side effect (observed in the scratch copy).
- check_forward_tests.py relies on `assert`, so `python -O` / PYTHONOPTIMIZE disables every check and it reports PASS. It also crashes on zero cases (:104). It must be rewritten with explicit errors before it becomes a generic package gate.
- The external-mount path (generator_inventory :206-211, validate_inventory :256-264, pin assets :788-790, canonical_pin_map :744-745) has zero corpus lines and no positive test. Extracting it unchanged carries untested code. Add a synthetic external fixture before claiming support.
- --online over all sources deterministically fails whenever any VOLATILE-HTML source exists (:1092). If the package exposes an online refresh command unchanged, users will see a guaranteed failure on the LED fixture.
- External_vendor_tokens (:298) requires a non-empty vendor list once any routing query has candidates. A new project with one component would have to add a made-up vendor name to pass. The generic profile must allow an empty list.
- validate_pin_assets reads the symbol library unconditionally (:770) and requires symbol_pin == footprint_pad (:797). Projects using standard KiCad libraries with alphanumeric or repeated pads (e.g. BGA 'A1', or several pads sharing one number) will fail. The generic profile should keep this strict check but make pin-asset validation conditional on cad.enabled, and should report 'not performed' rather than PASS.
- Critical-fact-review review logs must resolve inside the audit skill dir (:840-841). If generated projects keep evidence under .claude/skills but the audit skill logic moves to node_modules, AUDIT must become a configured project path, never the package dir, or hash-locked review logs cannot be found.
- LED docs contain false claims about the validator (validate.ts:15, ARCHITECTURE.md:198, :756, evidence.ts:248, integration.test.ts:297). Porting those comments into the package would spread wrong guidance to agents.
