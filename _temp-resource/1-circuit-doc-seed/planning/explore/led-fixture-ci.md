# led-fixture-ci: LED regression fixture (fixtures/led) and CI design inputs for Takazudo/zudo-circuit-doc

## Summary
I verified these results by running them, not only by reading the code. I used `git archive` to extract a minimal subset of zudo-led-lamp@194d8a2 (353 files, 56,261,304 bytes) into planning/prototypes/ led-min, then ran these checks unmodified against it:
- the pinned validator: `PASS: component-spec contract; 35 lines`
- its unit tests: 38/38 OK
- check_forward_tests.py: 5 integration cases, 7 negative routes
- check:components, check:models and check:footprint-previews: all passed
- generate.ts under other TZ/locale settings on Node 24.13.1 (CI uses Node 22): wrote 0 pages; every golden file's git blob id matched.

Generation is deterministic. The pipeline has no Date/random/cwd dependence, serializeReport is documented as having no timestamps (cli/run.ts:68-71), and the only npm packages the generator uses are mdast-util-to-markdown 2.1.2, mdast-util-gfm-table 2.0.0 and mdast-util-mdx 3.0.0. Golden bytes depend on those exact versions.

The validator never executes the board generator scripts. generator_inventory() (validate.py:192-223) reads board_p/board_l/swd_adapter_spec.py through a static AST DSL (ComponentDsl, validate.py:73-189) that refuses imports and calls. No kiutils, skip or KiCad is needed. The only Python execution is test_validate.py:44-53, which imports scripts/schgen/verify_power_switch.py (stdlib-only: board_l_spec, schgen_core, sexp) to test check_topology on NETS.

A subset of footprints works. parity.ts:26-47 only requires the master and .pretty directories to hold the same names with identical bytes, so 25+25 passes. STEP files are only existence-checked, never read (references.ts:185-187). WRL files are parsed and size-limited (references.ts:16-19, 180-188), and the public WRLs are byte-identical copies of the 3dshapes WRLs.

What to exclude, with evidence:
- manufacturing/ (7.15 MB)
- enclosure/, doc/enclosure-viewer and doc/public/assets/enclosure (~64 MB). These couple only through `pnpm build`'s generate:enclosure-viewer step (package.json:12, enclosure-viewer/build.mjs:12-23).
- boards/** (1.24 MB). Only CI regen-idempotency and the verify_* scripts read it; the validator does not.
- footprints/vendor, scripts/pcb, the 6 unselected footprints and 2 unselected model pairs
- doc/component-docs source (it becomes the runtime package)
- hand-authored content

Five of 451 generator tests fail in the minimal subset, all because of host-only inputs. The other 446 pass:
- narrative-links needs architecture/decisions.mdx and power/ratings-matrix.mdx
- presentation needs src/chrome-bindings.tsx and src/styles/global.css
- model-viewer imports src/component-model-viewer/*
- workflow-contract reads .github/workflows

LED CI (pr-checks.yml, main-deploy.yml, component-spec-skills.yml):
- Tools: Python 3.12 (setup-python), Node 22 (setup-node), pnpm 10.34.1 (from packageManager), and the google-chrome preinstalled on ubuntu-latest.
- No Docker, KiCad or Playwright.
- The model-viewer smoke drives Chrome over raw CDP (model-viewer-browser-smoke.mjs:58-68, override with CHROME_BIN).
- Footprint SVG regeneration is local-only through a Docker KiCad 9.0.9 image pinned by digest (config.ts:5-9, generate.ts:114-122). I did not re-run it: the image is not cached here.

The seed is correct on counts (31 footprints, 27 STEP+WRL pairs, 25 selected, 35 aliased records, no tracked PDFs). It is also right that validate_inventory ignores inventory.generator_specs (validate.py:238 calls generator_inventory() with no arguments). Where the seed is incomplete or the premise was wrong:
- There is no Python generator execution or kiutils/KiCad dependency.
- There is no Playwright in CI; enclosure-viewer/smoke.mjs uses Playwright but is not in CI or b4push.
- "fixtures/led: pinned corpus or loader" was left undecided; I recommend below.
- The seed never mentions that the golden MDX marker `# GENERATED by doc/component-docs — do not edit; run \`pnpm generate:components\`` is hard-coded at core/page.ts:26-27 and doubles as the ownership marker.
- It also misses that LED's doc/scripts/setup-doc-skill.sh is an older zudo-doc template (blob matches zudo-doc commit 4c2a508, 2026-07-19), not the v5.27.0 one.

That version gap matters. The v5.27.0 template adds LINK_TRACKED_SKILLS, on by default, which would symlink every project .claude/skills/* evidence bundle into ~/.claude/skills. A circuit template must pass --no-link-tracked-skills or otherwise account for it.

Licensing:
- zudo-led-lamp is PUBLIC with licenseInfo null and no LICENSE/NOTICE file; zudo-circuit-doc is PUBLIC with no license yet.
- The fixture's CAD is third-party: kicad_mod files carry an `easyeda2kicad:` module prefix, WRLs a `generated by easyeda2kicad.py` header, and STEP files SolidWorks `SwSTEP` headers.
- Exceptions are project-derived: SW-TH_SS-12D01-G020 STEP/WRL (Open CASCADE, derive-model.py) and the POT/IDC/SW footprints.
- Evidence bundles hold 120 short `evidence_extract` datasheet quotes (max 832 characters).

Recommendation: vendor the verified 353-file set into fixtures/led/, keeping the pinned repo-relative layout. That way the pinned validate.py (ROOT = parents[4]) and the `${KIPRJMOD}/../../footprints/kicad/zudo-led-lamp.3dshapes/` model prefix both resolve unchanged. Add:
- a byte lock (sha256 + git blob SHA-1)
- a sync/check script that re-derives the set from a local clone (`git archive`) or the GitHub codeload tarball
- NOTICE.md stating that fixtures/led is not covered by MIT
- package `files` whitelists plus a pack check that forbids fixtures/

The pinned validator stays in the fixture as a differential oracle.

## risks
- Licensing: zudo-led-lamp has no license, so the fixture's evidence JSON, golden MDX, spec DSL and schgen scripts are all-rights-reserved by default (the owner can relicense them). The easyeda2kicad footprints, WRLs and SolidWorks-exported STEP files are third-party EasyEDA/LCSC-sourced CAD with unknown redistribution terms, and the datasheet extracts are third-party text. Putting them under an MIT repo without a NOTICE would imply an MIT grant nobody has made.
- Repository bloat: vendoring STEP adds 45.9 MB raw (~8.2 MB compressed) permanently to git history. Dropping it later needs a history rewrite, which conflicts with the no-force-push rule. Decide before the first commit.
- Golden byte-compare will break on any mdast-util-to-markdown, mdast-util-gfm-table or mdast-util-mdx upgrade and on any change to GENERATED_MARKER (core/page.ts:26-27). The runtime must pin those deps exactly and let the fixture config supply the legacy marker; otherwise golden needs a normalization step, which weakens the check.
- Running the pinned LED validator's unit tests writes fixtures/led/tmp/pdfs (validate.py:1078 via online_sources), and python without -B writes __pycache__ into the fixture. CI must run on a temp copy, or gitignore those paths and assert `git status --porcelain fixtures/led` is empty afterwards.
- Pinned hard-coded LED counts and domains (25/35/91/8, EXPECTED_WITHHELD 6, 8 integration domains, STUSB/AL8860 locks) must move into fixture config or fixture-only tests. A generic runtime that keeps them will reject zero-component and new projects; one that drops them without fixture assertions loses regression protection.
- scan:artifacts SITE tier (MINIMUM_SITE_FILES 150, EXPECTED_WITHHELD 6, sitemap/llms checks) and the browser smoke (hard-coded record slugs) depend on the full LED built site, including hand-authored pages and enclosure assets. They cannot be reproduced byte-for-byte from the minimal fixture. The planner must re-baseline them per fixture or scope them to generated surfaces only.
- Adopting zudo-doc v5.27.0+ setup-doc-skill.sh in the circuit template makes LINK_TRACKED_SKILLS on by default, which may symlink the project's .claude/skills/* (evidence bundles, circuit-spec-integration) into the user's global ~/.claude/skills. The template should pass --no-link-tracked-skills or document it, and the scan harness must not hard-code 'doc-wisdom'.
- Upstream availability: the remote sync path depends on the LED repo staying public with the commit reachable (codeload or tree API). The local-clone `git archive` path and the committed lock keep offline checks working. Codeload tarball bytes are not stable, but the file contents inside are.
- Footprint SVG determinism under Docker regeneration is only claimed by the LED source (config.ts:7-8, generate.ts:115-118). This session did not re-verify it because the image is not cached. Keep regeneration a manual/local job and CI hash-check only.
- Node version: LED CI uses Node 22 with --experimental-strip-types. It was verified locally on Node 24.13.1 only. If the new packages ship .ts through strip-types, both 22 and 24 should be in the CI matrix.
